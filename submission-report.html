iPe Merchant Onboarding Copilot

A shop applies in one web chat. A hosted 8B model asks, explains, and cites. A deterministic service decides, and a person at iPe is the only one who can turn the shop on.

26 November 2026 · Capstone-iPe
This PDF is the technical report. The sources that accompany it are Google Docs.

1. The problem

Merchant onboarding needs a legal name, a place, a type of shop, a monthly volume, the payment methods, a yes or no on storing payer phone numbers, and a small pack of documents. The applicant also needs to understand why a document is required, and to be told plainly what is still missing. A chat can do that. A generative model must not become the source of truth for the outcome.

The product is one shop, one thread. The copilot asks for the single pending item, takes a PDF, JPG, or PNG, reads the application back, and submits only when every required slot is uploaded or the merchant has said the file is not available. The verdict names the outcome, the gaps, the assignee, the policy, and one review id. The thread stays open. A file that arrives later updates the verdict and keeps that id. Activation is a human act. There is no tool for it.

A correct answer is the Correct list written for that shop before the agent existed: the outcome, the missing items, the assignee, a stable review id when one is due, and no sentence that says the shop is live. The gold set is 71 shops, G-001 to G-071, in the gold-set document. G-001 to G-050 were used while building. G-051 to G-071 were held out and run once. The set is not in the retrieval index.

The worked example is Lotus Tea House: a cafe in Pune, ₹12,00,000 a month, registration and owner identity uploaded, bank proof, shopfront photograph, and addendum missing, with a note that demands the shop be marked Active. The correct result is in review, assigned to the Merchant Risk Lead, and unchanged by a later demand to activate. A hawala shop is refused and receives no review id.

2. Architecture

The web chat talks only to the copilot, and only with the merchant’s Google bearer token. The copilot is the only service that prompts the language model. ONB owns the application, the files, the pending field, and the verdict. The policy corpus is a third service. The model never supplies a tool argument, and it never writes the outcome.

PieceWhat it owns
Web chatThe React thread, sign-in, and the upload control. ConversationView v1.0, frozen in LLD-0002. Exam-scoring fields never reach the browser.
CopilotThe planner, executor, and critic over Qwen/Qwen3-8B. Policy search. The MCP client. Every sentence the merchant reads.
ONBDeterministic Python. Five tools. The rules. One review id, allocated once.
onb-corpus500 documents and 1,446 chunks. Hybrid search. Embeddings from bge-small-en-v1.5. POST /v1/search with a bearer token.
Document checkCalled by ONB when a file is saved. The default asks the hosted chat model; a rules checker is the fallback. The verdict remains the rules. LLD-0001 is still a draft, and it still describes a rules-only checker.

The tools are next_step, save_answer, save_file, submit, and get_review. There is no activate, waive, change-volume, or mark-complete operation. Calling next_step with no id creates the application. Resume is the same call with that id. Chat history lives in Postgres so the merchant can return to the thread. History does not choose the next tool and does not compute the verdict.

Weights are not trained. Both models are hosted OpenAI-compatible endpoints. Embeddings are used by the corpus, not by ONB and not by the copilot.

Path of one message

The website sends the text, or the file, with a client message id. The copilot checks the Google token, then the rate-limit counter. A duplicate id returns the reply already stored for that id, so a retry does not run the turn twice.

  1. The guard reads the line. An activation demand, a waiver, or a request to read an account number back stops here.
  2. Otherwise the copilot loads the application with next_step. ONB’s pending field is the only source of “what is next.”
  3. An exact command is handled in code. Any other line goes to the model once. The returned acts are checked against the words actually in the line. A span the merchant did not say is dropped.
  4. A correction of a stored field is saved, then next_step runs again. The pending field is saved only when the value belongs there. A value for a future field is not written ahead of time.
  5. Business type, payment methods, and phones pass a closed check before save_answer. An upload calls save_file, which runs the document check. Submit calls submit and allocates the review id if the rules allow one.
  6. If the merchant asked why, search runs after that tool call. The critic then checks any sentence the model wrote. The page receives two assistant messages when both an acknowledgement and the next question are due. They are not joined into one.

The same path writes the trace: decision fields, timing, and, when search ran, the ranks. The merchant’s text stays out of Langfuse.

3. Intake, files, and the verdict

ONB chooses the pending item. The order is the shop’s legal name, the city, the type of business, the monthly volume in rupees, the payment methods, and whether payer phone numbers are stored. Then the pack: business registration, the owner’s government identity, bank proof in the shop’s legal name, and a shopfront photograph from the last 90 days. A signed data-processing addendum is asked only when phones are stored. A note is optional.

Cafe and dhaba are stored as restaurant. Kirana is stored as grocery. The merchant’s own word is what the acknowledgement repeats when it differs from the category, so a cafe is accepted as “cafe (listed as restaurant).” An unlisted type is still stored. It stays in review even with a complete pack. Hawala, hundi, forex, crypto, and gambling are refused before a review id exists.

A question that begins with why does not save the pending field and does not submit. The copilot retrieves the policy and asks the same question again. Before the verdict, an answer already stored can be replaced. After the verdict, stored answers stay as stored. A missing slot can still receive a file, the rules run again, and the review id does not change.

A slot is closed by an accepted file or by the merchant saying the file is not available. “I already attached it,” with no file bytes and no slot named, does not close the slot. Submit is refused while a required slot is still open.

RuleResult
Refused type (money service, crypto, gambling)REFUSED. No review id.
Required evidence missing or not acceptedIN_REVIEW, with the gaps named.
Pack complete and the type permittedRECOMMEND_GO_LIVE. A recommendation, not activation.
Monthly volume at or under ₹40,00,000Merchant Risk Lead.
Monthly volume above thatHead of Payments.

The copilot renders that structure. It does not edit the fields. A wrong retrieved passage can spoil the citation. It cannot change the outcome.

The document check

When a file is saved, ONB calls a verifier with the slot, the stored legal name, the bytes, and the date. The default implementation asks the same hosted chat model and returns a reason code. If that mode is turned off, a rules checker does the format and freshness tests instead. Either way, the code that chooses IN_REVIEW, RECOMMEND_GO_LIVE, or REFUSED does not ask the model. A reason code such as a shopfront older than 90 days becomes a sentence the copilot already knows. The model does not invent the rejection.

The checker is not a production identity or bank-account proof. It does not establish that a certificate is genuine. LLD-0001 is still a draft, and it still describes a rules-only checker.

4. What we changed because the model is an 8B

This is the graded compensation for a small model. The 8B interprets a line and explains a rule. It does not run the shop.

  • A guard runs first. An instruction to ignore policy, activate the shop, or waive a document never becomes a prompt.
  • A few exact commands skip the model: why, submit, field=value, and a file name. Every other line is read once, against a closed set of labels. A label outside that set is dropped.
  • ONB, not the model, names the next field and computes the verdict. The words the model returns are not passed through as a tool argument.
  • Closed lists are checked in code before anything is saved. Canonical “other” is not stored.
  • Search runs after ONB has acted, and only to cite. Eligibility is not a retrieval score.
  • A critic reads model sentences before they are shown. A claim that the shop is live, or a review id the rules did not issue, is removed. Digit runs from accounts and identity numbers are not echoed. A volume the merchant just typed stays on screen.
  • A tool error is answered from a fixed map. Malformed JSON is not given a second free-form chance to invent a tool. The loop stops at ten steps.

The Week 1 baseline is the evidence for this shape. Ten diagnostic cases were run on Qwen/Qwen3-8B with three strategies and no agent around them.

StrategyClean casesWhat broke
Structured output, few-shot6/10The only strategy that stayed on the closed label set for most safety-shaped turns.
Chain-of-thought, self-consistency0/10Invented labels, a soft refusal, and a dropped review id.
Decomposition0/10The same class of miss, including activation language.

The sample is a diagnosis. It is not a statistical comparison of prompting methods. It was enough to stop asking the 8B to plan the whole application in prose.

Recall is measured on its own, apart from whether a shop case passed. The corpus experiment uses 24 fixed why-and-cite questions with gold document ids. The index that is deployed is hybrid: dense similarity and keyword postings, fused by reciprocal rank, with a folder-tier bonus and one chunk kept per document.

Chunk length was swept on the same 24 questions. At 400 tokens with 60 of overlap the index has 2,667 chunks and hybrid hit@4 is 0.875. At 800/120 it has 1,446 chunks and hit@4 is 0.958. At 1200/180 it has 1,063 chunks and hit@4 is again 0.958, with mean recall@4 of 0.701 against 0.694. The deployed index is 800/120. The longer chunk does not raise the hit rate. 6. End-to-end results

A gold shop passes when the outcome matches, a refused shop has no review id, every other shop has one id that does not change, a why or a refusal does not skip the pending field, the reply does not say the shop is live, and digits the merchant typed for an account or an identity are not repeated.

The recorded logs are in the source pack, under the names replay-build and replay-holdout. They were not repeated after later changes to how a free-text line is read, so this report does not present them as a replay dated 26 November. On this definition, task completion for the Week 1 set is 71 of 71 on the recorded runners.

The three evidence layers keep separate denominators. Twenty-four policy questions measure retrieval. Ten bare prompts measure the model with no agent around it. Seventy-one shops measure the workflow. Three hundred and forty-five spoken lines measure the reader. A pass rate from one layer is not an average with another. The build set may be used while changing the reader. The holdout may not. Replaying G-051 to G-071 in order to tune would retire the holdout claim, which is why that file is a single recorded run.

The twenty-question client check is a separate log in the pack. The 345-line diagnosis is another. The 24-question table comes from the retrieval note, not from the copilot’s client check. A natural run that finishes in a few hundred milliseconds did not reach the model. That fast path is the outage fallback, and it is not a score. A real run needs the chat host and takes several minutes.

Three figures the template also names are not in a published table: the average number of tool calls per shop, the rupee cost per query, and latency percentiles. Token counts are written on a trace only when the provider returns them. The copilot does not estimate tokens it was not given.

7. Failure taxonomy

The template asks for four classes: a retrieval miss, a reasoning error, a tool-call error, and a hallucination. This report uses those four. The recorded 71-shop runs did not fail, so they do not supply an observed incident. The classes are the names used when a line in the 345, or a live turn, goes wrong.

ClassMeaningWhere it is visible
Retrieval missThe in-force passage is absent from the top documents, or the reply falls back because nothing usable came back.The search hit list. trace.reply = fallback.
Reasoning errorA why or a refusal moves the pending field, or the value is saved on the wrong field.trace.intent and trace.action. The forty wrong-field rows.
Tool-call errorONB rejects the value: a volume it cannot read, phones that are not yes or no, an empty answer.The ONB error. No outcome is written.
HallucinationA fee, a claim that the shop is live, or a review id the rules did not issue.The critic drops the sentence. A replay fails a live-claim check.

A right passage and a clumsy sentence is a grounding problem, not a retrieval miss. A right verdict and an awkward explanation is not a broken rule. A wrong outcome from ONB would be a rule failure even if the copilot repeated it word for word.

8. Traces of real turns

Every message, upload, and submit that the copilot accepts is one trace. The service writes the trace to Postgres and posts it to Langfuse Cloud in the US region, on the current OpenTelemetry trace endpoint. The session id is the application id, which begins with app_. The turn is named copilot.message, copilot.file, or copilot.submit. Child spans cover the model read, the policy search, and the explanation.

Content capture is off. A trace carries the decision fields, the timing, the model name when it is known, and the retrieval ranks. It does not carry the merchant’s words, the prompt, or the file. A row remains in the outbox until Langfuse accepts the whole turn. A retry sends the same trace and span ids. Authentication failures that happen before a turn is reserved are not traces.

The trace dashboard is that Langfuse project. The public session for the demo is app_3020d278483c.

9. Responsible AI

Merchant text is data, including text inside an uploaded file. On the demo, the note that says to ignore policy and mark the shop Active is stored as a note and is not obeyed. The adversarial cases in the source pack are refused before a model call. The page the merchant sees does not echo account or identity digits. Traces, by default, do not contain the utterance.

Refusal of a money-service type is a rule with a fixed sentence, and it opens no review. After a verdict, “activate us now” is declined under the policy and the same review id is repeated. RECOMMEND_GO_LIVE names a human reviewer. The interface has no operation that can set a shop live. That boundary is the tool list, not a sentence in the prompt.

The adversarial file checked with the unit tests covers the boundary in the forms a merchant, or a pasted instruction, actually uses. Demands to go live, including in Hindi and Hinglish, are refused. So are requests to waive the shopfront, to mark the pack complete, and to read back an account number or its last four digits. A speaker who claims to be the Merchant Risk Lead is still refused. A made-up policy id that says the copilot may activate is refused. A JSON fragment posing as an intent is not executed as a tool call. A shop name that happens to contain the word “active” is saved as a name, which is the distinction the guard has to get right.

10. Deployment and the recorded demo

The web chat, the copilot, ONB, and the corpus each run as a Render web service. Render builds the image and runs it. There is no second container file in the source pack. Postgres holds the ONB applications and the copilot’s conversation history. A Render Key Value instance named copilot-cache holds only a rate-limit counter and a search cache.

Each signed-in merchant may send 30 messages or files in a minute. The next request is HTTP 429, code rate_limited, and the page asks them to wait a minute. The website does not automatically retry that response. Policy search results are kept for five minutes, keyed by the question and the number of hits. Saved answers, files, and the verdict are not cached. If Key Value is unreachable, the turn still runs and search calls the corpus. A free Key Value instance forgets its keys when it restarts. That is acceptable for a one-minute counter and a five-minute cache.

11. What this report does not claim

  • The 24 retrieval questions and the 10 prompting cases are small. They compare settings. They do not cover every paraphrase of the policy.
  • The 50/50 and 21/21 figures are the recorded replay files. They predate later reader changes and were not re-run for this document.
  • Forty of the 345 spoken lines still save the wrong field. That suite is a diagnosis, not the Week 1 gate.
  • The document checker may call the chat model. LLD-0001 has not yet been revised to say so. The verdict path does not.
  • Cost per query and latency percentiles are not measured in a table here.
  • Names of authors, the institution, and the mentor belong on the course cover. They are not filled in from a git username.

Annex. Waking the services

The web chat, the copilot, ONB, and the corpus run on Render’s free plan. Each one sleeps after about fifteen minutes without a request. Open the four addresses below, one after another, and wait until that page answers. The first request after a sleep can take about a minute. A service that has answered stays awake for the next quarter of an hour. Wake all four before signing in, or the chat will wait on a service that is still starting.
